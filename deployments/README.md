# Deployment

helixdesktop.org is one image, built from the repository's
[`Dockerfile`](../Dockerfile): the site generated by `nuxt generate` and
served by unprivileged nginx (uid 101) on port 8080, with `/healthz` for the
probes. It runs on Kubernetes from the Helm chart in
[`helm/charts/helix-web`](helm/charts/helix-web), with images in a
DigitalOcean Container Registry.

```
deployments/
  helm/
    charts/helix-web/   the chart (every option documented in values.yaml)
    VERSION             the chart version deploy.sh installs
    bump-version.sh     bumps VERSION and Chart.yaml together
    build-charts.sh     lints and packages charts into build/ (ignored)
    Makefile            bump-version, charts, lint
  environments/         local only, ignored by git except its .gitignore
    prod/
      helix-web-values.yaml   ingress host, TLS, image repository and tag
      kubeconfig.yaml         the cluster's kubeconfig
      manifests/              optional extra objects, applied before the chart
infrastructure/scripts/
  set-context.sh        points KUBECONFIG at environments/<env>/kubeconfig.yaml
  deploy.sh             helm upgrade --install of the packaged chart
  _repo-common.sh       shared paths and the project name (= namespace)
.github/workflows/build-image.yml   builds and pushes the image (manual)
```

The routine, from a workstation:

```sh
# 1. Build and push the image: GitHub > Actions > Build image > Run workflow.
# 2. If the chart changed, bump its version and package it:
make upgrade-charts                 # patch; BUMP=minor, BUMP=major or BUMP=1.2.3
# 3. Deploy:
make build-charts                   # if not done in step 2 (build/ is not committed)
make deploy-prod                    # or IMAGE_TAG=<tag> to deploy one build
```

`make help` lists the targets, `make check-prereqs` the tools they use.

## Build and push

[`.github/workflows/build-image.yml`](../.github/workflows/build-image.yml) is
manual-dispatch only. It builds the `Dockerfile` for linux/amd64 and pushes two
tags:

| Tag | Moves | For |
| --- | --- | --- |
| `latest` | every build (unless the run unticks it) | what the prod values file deploys |
| `<commit>-spec-<spec commit>` | never | rolling out, or back to, one exact build |

The docs are generated from helixdesktop/spec, so a build has two inputs: this
repository's commit and the spec's. The run's `spec_ref` input picks the
spec's branch or tag (default `main`), and the immutable tag names both
commits.

Nothing runs on push. Production pulls `latest`, which pods re-pull when they
restart, so an automatic build would change what the site serves at its next
reschedule.

Where the image goes is a property of a deployment, not of this repository, so
the workflow reads it from configuration (Settings > Secrets and variables >
Actions), and a fork owes the file no edit:

| Setting | Kind | Purpose |
| --- | --- | --- |
| `IMAGE_REPOSITORY` | variable | Image path, e.g. `registry.digitalocean.com/<registry>/helix-web`. Required: the run fails with a clear message if unset. |
| `REGISTRY_USERNAME` | secret | For DigitalOcean, an API token with read/write registry access. |
| `REGISTRY_PASSWORD` | secret | For DigitalOcean, the same API token. |
| `DOCKER_CONFIG_JSON` | secret | Alternative: a whole docker config, `auths` and all, e.g. the output of `doctl registry docker-config --read-write`. Takes precedence when set. |

The registry host is derived from `IMAGE_REPOSITORY` rather than configured
separately, so there is no second setting that could disagree with it.

A config pasted straight from a workstation often does not work, and the
workflow says so before building rather than failing on the push: Docker
Desktop keeps credentials in the OS keychain and leaves `auths` empty. The
`doctl` output above has a real `auths` entry.

`IMAGE_REPOSITORY` has to match `image.repository` in the prod values file:
the workflow decides where images land, the values file where the cluster pulls
them from, and nothing checks that the two agree.

## Deploy

`make deploy-prod` runs, from the workstation:

```sh
source infrastructure/scripts/set-context.sh prod      # KUBECONFIG=deployments/environments/prod/kubeconfig.yaml
infrastructure/scripts/deploy.sh prod helix-web
```

which installs `deployments/helm/build/helix-web-<VERSION>.tgz` as release
`helix-web` in namespace `helix-web` (created if missing), with
`deployments/environments/prod/helix-web-values.yaml`, and waits for the
rollout. Anything in `deployments/environments/prod/manifests/` is applied to
the namespace first. `deploy.sh` stops before touching the cluster if the
package or values file is missing, or the values file still has a
`FILL-ME-IN` placeholder.

A new image under `latest` does not change the release, so `helm upgrade`
alone leaves the running pods alone. Either restart them (they re-pull, with
`pullPolicy: Always`):

```sh
kubectl --namespace helix-web rollout restart deployment/helix-web
```

or deploy the build's immutable tag, which the workflow's run summary prints:

```sh
make deploy-prod IMAGE_TAG=1a2b3c4-spec-5d6e7f8
```

That is also the rollback: deploy an older immutable tag. The next plain
`make deploy-prod` returns to `latest`.

## Environments

**Nothing under `environments/` is committed.** The directory holds a cluster
kubeconfig, so it is ignored wholesale: the chart is where the shape of a
deployment lives, and these files only fill it in. To set up prod on a new
machine:

```sh
mkdir -p deployments/environments/prod
doctl kubernetes cluster kubeconfig show <cluster> > deployments/environments/prod/kubeconfig.yaml
```

and a `helix-web-values.yaml` beside it along these lines:

```yaml
image:
  repository: registry.digitalocean.com/<registry>/helix-web
  tag: latest
  pullPolicy: Always
imagePullSecrets:
  - name: registry-<registry>
ingress:
  certManager:
    clusterIssuer: <your ClusterIssuer>
  hosts:
    - host: helixdesktop.org
      paths:
        - path: /
          pathType: Prefix
  tls:
    - secretName: helixdesktop-org-tls
      hosts:
        - helixdesktop.org
```

### Pulling from the DigitalOcean registry

The registry is private, so the pods need a pull secret. Two ways to get one:

- **The DOKS registry integration** (`doctl kubernetes cluster registry add
  <cluster>`, or the registry's settings in the control panel). DigitalOcean
  then keeps a `registry-<registry>` secret in the cluster's namespaces and
  adds it to each namespace's `default` service account. The chart runs its
  pods under a service account of its own, so name the secret in
  `imagePullSecrets` as above (or set `serviceAccount.create: false` to use
  `default`). Check that it is there with
  `kubectl --namespace helix-web get secret registry-<registry>`.
- **A secret of your own**: `doctl registry kubernetes-manifest --namespace
  helix-web > deployments/environments/prod/manifests/registry.yaml` writes one
  named `registry-<registry>` that `deploy.sh` applies before the chart. It
  holds a credential, which is why `manifests/` lives in the ignored
  environment directory.

## Chart version

`deployments/helm/VERSION` is the chart version `deploy.sh` installs, and
`bump-version.sh` keeps it and `Chart.yaml`'s `version` equal (`build-charts.sh`
refuses to package if they differ):

```sh
make bump-charts-version              # 0.2.0 -> 0.2.1
make bump-charts-version BUMP=minor   # 0.2.1 -> 0.3.0
make bump-charts-version BUMP=major   # 0.3.0 -> 1.0.0
make bump-charts-version BUMP=1.4.0   # exactly this (SemVer, pre-releases too)
make upgrade-charts [BUMP=...]        # bump, then build
```

Bump it whenever the chart's templates or defaults change, and commit
`VERSION` with `Chart.yaml`. `appVersion` names the site's release and is left
alone. The packages in `deployments/helm/build/` are derived and ignored: run
`make build-charts` in a fresh checkout before deploying.
